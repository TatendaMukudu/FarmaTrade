# P0.6 review — the source ceiling does not bite on a packaged source

Reviewer: Claude. Subject: `codex/p06-source-commitment` (PR #29), commits
`f107080` and `182071d`, reviewed against
`claude/farmatrade-intelliqs-improvements-e4nexp` at `988d74b`.

## Verdict

The implementation is sound and I could not break it on the axes I attacked
first. **One real gap survives**, and it is not Codex's alone — it lives in the
seam between P0.5's deliberate refusal to convert packages and P0.6's reuse of
`fitsWithin`. I wrote `fitsWithin`. The permissive default is mine.

## What I attacked and could not break

- **Lock ordering.** `lockSupplySource` takes the `ProduceStock`/`Livestock`
  row before `lockIntents`. A match carries at most one SUPPLY intent, so a
  transaction holds at most one source lock, and the intent locks stay ordered
  by id. No cycle is constructible. `proposeTerms` and `closeEngagement` take
  intent locks without a source lock and never wait on a source, so they cannot
  close one either.
- **Unresolvable source unit.** I expected `PRODUCE_UNIT_CANONICAL[source.unit]`
  to miss and silently disable the ceiling. It cannot: the map is total over the
  closed `ProduceUnit` enum, so a stock row's unit always resolves. The farmer's
  own words live elsewhere, exactly as `PRODUCT_TRUTH.md` requires. **My
  hypothesis was wrong and the probe that tested it failed.**
- **Rule duplication.** The ceiling is computed through `readCapacity` and
  `fitsWithin` rather than a second copy of the arithmetic. Law 8 holds.
- **Equipment.** Excluded with a stated reason — reusable, time-dependent, no
  scheduling model — rather than guessed at. That is the correct application of
  "unknown stays unknown."

## The gap: a PACKAGE source does not bound a mass-denominated agreement

`fitsWithin` returns `fits: true` on three paths that all mean *"there is
nothing to check here"*:

```
if (required == null)            return { fits: true }   // no quantity on the terms
if (reading.remaining === null)  return { fits: true }   // source declared no ceiling
if (!contribution.ok)            return { fits: true }   // not measurable against this basis
```

That default is right for an **intent's own** authorized ceiling: an owner who
never stated a quantity has not declared exhaustion, and P0.3 turns on that
distinction. It is wrong for a **physical source cap**, where "not measurable"
must not read as "unlimited."

`BAG` and `CRATE` are `PACKAGE` units with `factor: null` — P0.5 refuses to
convert them to mass, on purpose, because a bag is not reliably a weight. So
when the stock row is in bags and the agreement is written in kilograms,
`contributionOf` returns `unknown_unit`, `fitsWithin` returns `fits: true`, and
the source ceiling silently does not apply.

Probed against `capacity.ts` directly (pure, no database):

```
readCapacity({ quantity: 500, unitCode: "BAG" }, [])   // remaining: 500
fitsWithin(reading, 9_000_000, "KILOGRAM").fits        // true
fitsWithin(reading, 900, "BAG").fits                   // false — bites correctly
```

Nine million kilograms passes a five-hundred-bag ceiling. The same ceiling
bites correctly when both sides speak the same package, so the guard works;
it is the unmeasurable case that leaks.

This is not exotic. Maize stored in bags is the ordinary case in the markets
`measurement.ts` names, and P0.6 exists to stop exactly this class of
over-promise.

## Why this is a product question, not a patch

The fix is one line in shape and a decision in substance: when a physical
source cannot be measured against the terms, does FarmaTrade

1. **refuse** the acceptance (`fits: false`) — safe, but blocks a legitimate
   trade whenever a farmer's stock and their buyer's terms use different
   dimensions, which P0.5 says is common and honest; or
2. **permit and surface it** — the agreement forms, and the overcommitment is
   reported as an unmeasured reservation, consistent with how `CapacityReading`
   already reports `unmeasured`; or
3. **require the terms to be denominated in the source's own unit** when the
   source is packaged — narrowest, and it keeps the farmer's words intact.

This is the same fork as RFC #21 Q1 (prevent versus surface), reappearing one
layer down. It should be answered by the founder rather than chosen here. I
have not implemented any of the three.
